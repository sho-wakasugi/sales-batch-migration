# 売上CSV集計バッチ ― Java から Python への移行と現新一致の検証

Java（Spring Batch）で業務バッチを作り、それを Python に移行しました。さらに、**同じ入力に対して両方の結果がバイト単位で一致すること（現新一致）**を、比較スクリプトで検証しています。

システム移行の流れ（元のシステムを作る → 移行する → 一致を確かめる）を、小さな題材で一通り行ったポートフォリオです。

## 目的

- **Java・Spring Batch の学習**：業務バッチでよくある処理を一通り実装しました。
  - CSV 取込
  - 入力チェック
  - エラー行の出力
  - DB 登録
  - 集計
  - 件数ログ
- **システム移行の進め方の実践**：移行で一番難しいのは「書き換えること」ではなく、「本当に同じ結果になっているかを確かめること」です。このリポジトリでは、次のことに取り組みました。
  - 現新一致の検証の仕組みを作る
  - 移行の途中で見つかった、仕様書に書かれていない動きに対処する

## 全体の流れ

```
 ① Java版を作る              ② Python版に移行する            ③ 現新一致を検証する
┌──────────────────┐      ┌──────────────────────┐      ┌───────────────────────────┐
│ java/            │      │ python/              │      │ python/tools/compare.ps1  │
│ Spring Batch     │ ───▶ │ 標準ライブラリ＋SQLite │ ───▶ │ 同じ入力で両方を実行し、    │
│ ＋MyBatis＋H2    │      │ Java と1対1で対応      │      │ ファイル・DB・件数・       │
│ JUnit 44件       │      │ pytest 118件         │      │ 終了コードを突き合わせる    │
└──────────────────┘      └──────────────────────┘      └───────────────────────────┘
                                    ▲                               │
                                    └──── 境界ケースで見つかった ────┘
                                          Java の動きを Python に反映
```

バッチの処理内容は、Java 版・Python 版で共通です。

1. 売上 CSV（売上日、店舗コード、商品コード、数量、単価）を読み込む
2. 入力チェックを行う（必須、数値、日付形式、数量は1以上）。エラー行は理由付きで `error.csv` に出し、処理は続ける
3. 正常データを売上テーブルに登録する
4. 店舗別・月別の売上金額と件数を集計し、`summary.csv` に出す（店舗コード、年月の昇順）
5. 読込件数・登録件数・エラー件数をログに出す

## 検証結果

### 現新一致：5種類の入力すべてで一致

| 入力 | 内容 | 結果 | 終了コード（Java / Python） |
|---|---|---|---|
| `input/sales.csv` | 本番想定の100行（エラー行10行を含む） | 一致 | 0 / 0 |
| `edge_cases.csv` | 境界ケース38行（特殊な空白、全角数字、long の上限、0年、クォート、CRLF、絵文字、不正なバイトなど） | 一致 | 0 / 0 |
| `edge_comment.csv` | `#` で始まる行を含む | 一致 | 0 / 0 |
| `failure_sum_overflow.csv` | 集計の合計が long の上限を超える | 一致 | 5 / 5 |
| `failure_single_quote.csv` | 項目が `"` 1文字だけの行を含む | 一致 | 5 / 5 |

比較した項目は次のとおりです。

| 比較項目 | 比較方法 |
|---|---|
| error.csv / summary.csv | **バイト単位**（文字コード・改行・クォートの違いも検出できる） |
| 売上テーブル | id と登録日時を除いた全行 |
| ログの件数と終了ステータス | 件数・ステータスの行を比較 |
| 終了コード | 値を比較 |

異常終了するケースも、Java と同じ条件で同じように異常終了することを確かめています。

### テスト：すべて成功

- **Java 版**：JUnit 44件。入力チェックの境界値、正常行とエラー行の振り分け、ジョブ全体の実行、異常終了を確認します。
- **Python 版**：pytest 118件。主な内容は次のとおりです。
  - Java のテストと同じ観点のテスト
  - Java の実際の出力とのバイト一致
  - Java と動きを合わせた点のテスト
  - Java 版のファイルのコピーが、元のファイルと同じであることの確認

## 移行で判断した点

最も大きな判断は、**移行の基準を「仕様書」ではなく「Java の実際の動き」にしたこと**です。

境界ケースで Java 版を実際に動かしたところ、仕様書に書いていない動きがいくつも見つかりました。現新一致を目的とする以上、Python の自然な書き方ではなく、Java の動きに合わせました。

| 観点 | Java の実際の動き | Python でそのまま書くと | 対応 |
|---|---|---|---|
| CSV の分割 | 項目の途中の `"` からクォート中の扱いになる。クォートの外の空白は削除する | `csv` モジュールでは結果が変わる | Spring Batch の処理を移植し、Spring Batch 本体と同じ結果になることを確認 |
| `#` で始まる行 | エラーにならず、黙って読み飛ばされる | 普通の1行として読む | 同じく読み飛ばす（Java 側の問題点として記録） |
| 空白の判定（trim） | NBSP（U+00A0）は空白とみなさない | `str.strip()` は NBSP も削除する | Java と同じ判定を実装 |
| 整数 | long の範囲。全角数字はエラー | `int` に上限が無く、`\d` は全角数字にも一致する | `[0-9]` と範囲チェックで再現 |
| 日付 | `0000-01-01` を正しい日付として扱い、集計では `0001-01` と出す | `datetime.date` は0年を扱えない | 日付を文字列で持ち、自前で検証 |
| 並び順 | UTF-16 の単位で比較する | SQLite は UTF-8 のバイト順（絵文字の順序が変わる） | SQLite に Java と同じ比較規則を登録 |
| 異常終了 | 集計のあふれなどで、ジョブ全体が止まる | 正しく処理できてしまう | 同じ条件で異常終了させる |

ほかにも、次のように判断しました。

- **外部ライブラリを使わない**：本体は標準ライブラリだけで作りました。外部ライブラリはテスト用の pytest だけです。
- **decimal を使わない**：金額は整数なので、端数は出ません。
- **実行履歴は移行しない**：Spring Batch のメタデータテーブル（実行履歴）は移行していません。

移行の途中で見つかった Java 版の問題（`#` の行が消える、集計のあふれでジョブが止まる など）は、Java を修正せずに記録しました。仕様として決め直すべき点として、[python/docs/migration-notes.md](python/docs/migration-notes.md) にまとめています。

## AI の使い方

開発には **Claude Code**（Anthropic の AI コーディングエージェント、モデルは Claude Opus 5.5）を使いました。AI が関わったコミットには、`Co-Authored-By: Claude` を付けています。

### 進め方

1. **本人が要件と方針を指示する**：使用技術、処理内容、標準ライブラリを優先すること、Java のコードは変更しないこと、などです。
2. **AI が計画を出し、本人が確認してから実装する**：作業ごとに、必ず先に計画を日本語で説明させました。AI が出した確認事項に、本人が答えてから進めています。
3. **AI が実装とテストを行い、区切りごとにコミットする**
4. **本人が結果を確認し、方針を修正する**：本人の判断で修正した例は次のとおりです。
   - Java 版：毎回テーブルを全件削除する案に対して、「それではバッチの意味がない。比較検証のときだけ削除する」と修正した
   - 構成：Python 版を別のリポジトリに分け、公開時に1つのリポジトリにまとめた
   - 公開前：コミット履歴の作成者情報を整理した

### AI の出力をそのまま信用しないための工夫

- **AI の推測ではなく、Java を実際に動かして期待値を作った**：境界ケースを Java 版で実行し、その出力を期待値にしました。
- **ライブラリの動きは、本体を直接呼んで確かめた**：次の2つは、Java で実際に実行して、Python 側のテストと照らし合わせました。
  - CSV の分割（Spring Batch の `DelimitedLineTokenizer`）
  - 空白の判定（Java の `Character.isWhitespace`）
- **一致の確認を自動化した**：比較スクリプトで、ファイル・DB・件数・終了コードをまとめて突き合わせます。比較が空振りしていないことも確かめました。

## 動かし方（概要）

前提は JDK 21 と Python 3.12（Windows / PowerShell）です。詳しい手順は、各フォルダの README を見てください。

```powershell
# Java版：ビルド（テスト44件も実行）と実行
cd java
.\mvnw.cmd clean package
java -jar target\sales-batch.jar clear=true

# Python版：準備、テスト（118件）、実行
cd ..\python
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe -m pytest
.venv\Scripts\python.exe -m salesbatch clear=true

# 現新比較（Java版をビルドしてから、python フォルダで実行）
.\tools\compare.ps1
```

## コミット履歴について

Java 版と Python 版は、もともと別々のリポジトリで開発しました。公開のために、両方のコミット履歴を残したまま、`java/` と `python/` のフォルダに移して1つのリポジトリにまとめています。

Python 版は最初、Java 版のリポジトリの中で作りました。そのため、Python 版の初期のコミットは、Java 版の履歴（`java/python/` の下）と Python 版の履歴（`python/` の下）の両方に見えます。
